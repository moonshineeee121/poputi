# Сценарии сайта авторских туров

Здесь хранятся BDD-спецификации всех семи основных возможностей из [описания продукта](../docs/product.md). Крупные возможности разделены на самостоятельные файлы, поэтому файлов десять. В каждом файле одна функциональность и несколько сценариев.

## Как читать сценарии

- `# language: ru` задаёт русский язык Gherkin. Файлы сохранены в UTF-8.
- `Функциональность` описывает одну возможность и её пользу.
- `Предыстория` задаёт условия заново перед каждым сценарием файла.
- `Дано` описывает исходное состояние, `Когда` — действие, `Тогда` — ожидаемый результат. `И` продолжает предыдущую группу шагов.
- `Структура сценария` с таблицей `Примеры` задаёт отдельный случай для каждой строки. Например, количество мест 0 и количество мест -1 — разные случаи одного правила.
- Таблица под шагом — данные этого шага, а не дополнительные сценарии. Формулировка «только следующие» требует точного состава результата; «в следующем порядке» дополнительно требует указанную последовательность.

## Условия подготовки данных

Каждый сценарий независим от остальных. Пользователи, туры, выезды и брони подготавливаются заново; результат предыдущего сценария не используется. Указание нового текущего времени или состояния в сценарии заменяет соответствующее исходное условие из предыстории.

В таблицах указаны существенные для конкретного правила данные. При автоматизации недостающие обязательные поля заполняются корректными фиксированными значениями. Число свободных мест подготавливается вместимостью и подтверждёнными бронями; отдельное несогласованное число свободных мест не задаётся. Отменённые брони места не занимают.

Все даты и время в соответствующих файлах проверяются относительно явно заданных тестовых часов. Наступление даты из примера в реальном календаре не должно менять результат.

Денежные значения в текущих примерах заданы целыми рублями за одно место. Ограничения и порядок фильтрации, отмены и изменения условий выезда описаны в [рабочих правилах продукта](../docs/product.md).

## Статус автоматизации

Четыре файла связаны с приложением и выполняются через `tests/bdd/test_core.py`: `accounts/registration.feature`, `accounts/authentication.feature`, `bookings/create_booking.feature` и `bookings/cancel_booking.feature`. Это 39 конкретных примеров. Дополнительно есть 17 HTTP/интеграционных проверок в `tests/test_web.py`. Запуск — `python -m pytest -q` при работающем PostgreSQL.

Остальные шесть файлов остаются спецификациями: их Python-шаги ещё не реализованы. Общая синтаксическая проверка всех десяти файлов подтверждает корректность Gherkin, но не выполнение неавтоматизированных сценариев приложением. Буквенно-цифровые обозначения броней в примерах используются как логические имена тестовых объектов; в интерфейсе приложение выдаёт собственные уникальные номера.

Сценарии об одновременных действиях должны исполняться с действительно пересекающимися запросами через отдельные соединения. Два последовательных запроса не проверяют гонку за последнее место или повторный возврат мест.
