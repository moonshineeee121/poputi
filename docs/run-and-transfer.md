# База данных, ручной запуск и перенос «Попути»

Проверено по исходникам и работающему PostgreSQL 22 октября 2026 года. Команды рассчитаны на Windows x64 и PowerShell. Выполняйте их из корня проекта; после ошибки исправьте её перед следующим шагом.

## 1. Устройство проекта

Это серверное приложение Django: браузер отправляет запрос, Python-код обращается к PostgreSQL через Django ORM и возвращает HTML из шаблонов.

| Файлы | Назначение |
| --- | --- |
| `manage.py` | Команды Django: сервер, миграции, создание администратора |
| `config/settings.py` | Настройки приложения, чтение `.env`, подключение к БД |
| `accounts/` | Пользователи, регистрация и вход |
| `tours/` | Туры, выезды, поиск и демонстрационные данные |
| `bookings/` | Брони и транзакционная работа с количеством мест |
| `templates/`, `static/` | HTML, CSS, JavaScript и локальные фотографии |
| `scripts/setup_local.py` | Загрузка PostgreSQL и изображений, запуск и остановка БД |
| `scripts/prepare.py` | Миграции, демоданные, проверка настроек |
| `scripts/start.ps1` | Объединяет подготовку и запуск сайта |
| `pyproject.toml`, `uv.lock`, `.python-version` | Зависимости, закреплённые версии пакетов, версия Python |
| `compose.yaml` | Альтернативный запуск PostgreSQL в Docker |

Нужен **Python 3.13.x**: в проекте задан диапазон `>=3.13,<3.14`. При проверке установлены Python 3.13.17, Django 5.2.18, psycopg 3.3.6 и PostgreSQL 17.11. Версии Python-пакетов восстанавливаются командой `uv sync --locked`.

Node.js, npm и отдельная сборка интерфейса не требуются. Docker-файл приложения отсутствует: Compose запускает только БД.

## 2. Где хранится база

Подключение по умолчанию задано в `config/settings.py:35–43`:

~~~text
Хост:         127.0.0.1
Порт:         54329
База:         poputi
Пользователь: poputi
Пароль:       poputi_dev

DATABASE_URL=postgresql://poputi:poputi_dev@127.0.0.1:54329/poputi
~~~

Приложение читает `.env` из корня проекта. Сейчас этого файла нет, поэтому действуют значения по умолчанию, если их не переопределяют переменные среды. Образец настроек — `.env.example`. Уже заданные переменные среды имеют приоритет перед `.env`.

**Фактические данные нынешней БД находятся вне проекта:**

~~~text
C:\Users\NotFooound\AppData\Local\Temp\poputi-302c83476c\data
~~~

Путь подтверждён запросом к работающему серверу. PostgreSQL может показывать его с коротким именем пользователя `NOTFOO~1`.

Правило в `scripts/setup_local.py:14–23`:

- Если задана `POPUTI_RUNTIME_DIR`, используется указанный корень runtime.
- Иначе на Windows при не-ASCII символах в полном пути проекта используется `%TEMP%\poputi-<хеш пути проекта>`.
- В остальных случаях используется `.runtime` внутри проекта.

Нынешний путь содержит `_Уник`, поэтому выбрана папка Temp. Runtime содержит `data/`, рабочую копию `postgres/` и `postgres.log`. В `.tools/postgres/` лежат исходные исполняемые файлы PostgreSQL, а не текущие таблицы приложения.

**Копирование одной папки BDD не перенесёт пользователей и брони.** Перемещение или переименование проекта может изменить вычисляемый путь runtime. Старые данные при этом могут оставаться в старом каталоге.

Для постоянного хранения лучше закрепить путь вне Temp, например `POPUTI_RUNTIME_DIR=C:/poputi-data`. Для существующей БД сначала выполните процедуру из раздела 7: простая смена пути на пустой каталог создаст новую БД.

## 3. Как создаются база, таблицы и записи

Последовательность `scripts/start.ps1`:

1. Если отсутствует `.venv/Scripts/python.exe`, выполняет `uv sync --locked`.
2. Без `-ExternalDatabase` подготавливает и запускает переносимый PostgreSQL.
3. Вызывает `scripts/prepare.py`: `migrate` → `seed_demo` → `check`.
4. Запускает `manage.py runserver 127.0.0.1:8000`.

Создание PostgreSQL находится в `scripts/setup_local.py`:

| Строки | Действие |
| --- | --- |
| 52–66 | Загрузка закреплённого дистрибутива PostgreSQL 17.11 Windows x64 с EDB в `.tools/downloads/postgres.zip`, распаковка в `.tools/postgres/` |
| 69–82 | Копирование исполняемых файлов в runtime; при отсутствии `data/PG_VERSION` — инициализация кластера через `initdb.exe` |
| 80 | UTF-8, локаль C, SCRAM, начальная административная роль `poputi` с паролем `poputi_dev` |
| 83–85 | Проверка состояния и запуск через `pg_ctl.exe` на `127.0.0.1:54329` |
| 86–89 | Проверка существования базы `poputi` через `psql.exe`; при отсутствии — создание через `createdb.exe` |

После `createdb` база ещё не содержит таблиц приложения. Их создаёт команда **`manage.py migrate`**, применяя сохранённые миграции:

| Миграция | Результат |
| --- | --- |
| `accounts/migrations/0001_initial.py` | Пользователь и связи с группами и разрешениями |
| `tours/migrations/0001_initial.py` | Туры и выезды, внешние ключи и ограничения |
| `tours/migrations/0002_search_normalization.py` | Нормализованные поля поиска и их заполнение для существующих туров |
| `bookings/migrations/0001_initial.py` | Брони, связи с пользователями и выездами, ограничения |
| Встроенные миграции Django | Группы, разрешения, сессии, журнал админки и служебные таблицы |

Главные таблицы:

- `accounts_user` — пользователи сайта.
- `tours_tour` — туры, каждый связан с организатором.
- `tours_departure` — выезды тура: даты, цена, вместимость, число занятых мест.
- `bookings_booking` — брони: пользователь, выезд, места, цена на момент бронирования, статус.

Модели определены в `accounts/models.py`, `tours/models.py`, `bookings/models.py`. Изменение модели само по себе таблицы не меняет. При разработке создают новую миграцию, затем применяют её. Для запуска и переноса готового проекта `makemigrations` не нужен: миграции уже включены.

Команда **`seed_demo`** реализована в `tours/management/commands/seed_demo.py:21–36`. Она создаёт организатора `travel_guide`, шесть туров и по три будущих выезда для туров без будущих выездов. Даты зависят от дня запуска. Повторный вызов не удаляет брони, но может добавить выезды, когда старые уже прошли. Организатор создаётся без пригодного для входа пароля и без прав администратора.

Регистрация и бронирование записывают данные через ORM. В `bookings/services.py` создание и отмена брони используют `transaction.atomic` и блокировки `select_for_update()`; одновременно меняется число занятых мест. Ограничения таблиц проверяют положительные значения, вместимость и уникальность повторного запроса. Текущая конфигурация принимает только PostgreSQL.

## 4. Ручной запуск на нынешнем ПК

В PowerShell:

~~~powershell
Set-Location -LiteralPath 'E:\python_proj\_Уник\BDD'
.\.venv\Scripts\python.exe -X utf8 scripts\setup_local.py start
.\.venv\Scripts\python.exe -X utf8 manage.py migrate
~~~

Если нужны демонстрационные туры или новые выезды вместо прошедших:

~~~powershell
.\.venv\Scripts\python.exe -X utf8 manage.py seed_demo
~~~

Проверьте настройки и запустите сайт:

~~~powershell
.\.venv\Scripts\python.exe -X utf8 manage.py check
.\.venv\Scripts\python.exe -X utf8 manage.py runserver 127.0.0.1:8000
~~~

Откройте [сайт](http://127.0.0.1:8000/). Терминал с Django оставьте открытым. При работающей БД и актуальной схеме для повседневного запуска достаточно команды `runserver`. Активировать окружение не требуется: вызывается его Python напрямую.

Для другого порта сайта замените `8000` на `8001`; порт БД от этого не меняется.

Если нужен администратор:

~~~powershell
.\.venv\Scripts\python.exe -X utf8 manage.py createsuperuser
~~~

Откройте [админку](http://127.0.0.1:8000/admin/). Администратор Django и роль PostgreSQL — разные учётные записи. Пароль `poputi_dev` относится к БД, а не к входу на сайт.

Остановить Django: Ctrl+C в его терминале. База остаётся отдельным процессом. Остановить её:

~~~powershell
.\.venv\Scripts\python.exe -X utf8 scripts\setup_local.py stop
~~~

Сокращённый запуск с подготовкой:

~~~powershell
.\scripts\start.ps1
~~~

Если PowerShell блокирует скрипты, используйте Python-команды выше или запуск для отдельного процесса:

~~~powershell
powershell -ExecutionPolicy Bypass -File .\scripts\start.ps1
~~~

## 5. Перенос на другой Windows-ПК с новой базой

Этот вариант создаст демонстрационную копию без прежних пользователей и броней. Для сохранения данных нужен раздел 6.

### Перенос через GitHub

Через GitHub переносите исходники, миграции, `uv.lock`, `.python-version`, `.env.example`, шаблоны, фотографии из `static/`, тесты и документацию. После клонирования на новом ПК выполните подготовку окружения и запуск из этого раздела.

В `.gitignore` исключены виртуальное окружение, скачанные исполняемые файлы, runtime PostgreSQL, локальные `.env`, дампы, каталоги `transfer/`, `backup/` и `backups/`, кеши и отчёты. Корневой `test.py` содержит только локальный эксперимент `print(123)` и также исключён; каталог настоящих тестов `tests/` сохраняется.

Поэтому клонирование репозитория не перенесёт существующих пользователей и брони. Для них отдельно передайте дамп и восстановите его по разделу 6. В нынешней копии рабочая БД расположена за пределами проекта, в Temp, и при добавлении исходников в Git не попадает в репозиторий.

### Подготовка файлов и окружения

Скопируйте исходники и ресурсы проекта: приложения, миграции, `scripts/`, `templates/`, `static/`, `manage.py`, `pyproject.toml`, `uv.lock`, `.python-version`, `.env.example`, а также документацию, тесты и `compose.yaml`, если они нужны.

Особенно сохраните `static/img/*.jpg`: в БД хранятся только относительные пути фотографий.

**Не переносите `.venv/` как готовое окружение.** Нынешний `pyvenv.cfg` ссылается на абсолютный путь Python на диске E:. На новом ПК создайте окружение заново. Кеши и старую `.runtime/` для этого варианта переносить не нужно.

Каталог `.tools/postgres/` можно скопировать на другой Windows x64, чтобы избежать загрузки PostgreSQL. Весь `.tools/` переносить необязательно. Первый запуск с загрузками требует интернета.

Пример нового расположения: `C:\projects\poputi`. Установите uv по [официальной инструкции](https://docs.astral.sh/uv/getting-started/installation/):

~~~powershell
powershell -ExecutionPolicy Bypass -c "irm https://astral.sh/uv/install.ps1 | iex"
~~~

Откройте новый PowerShell:

~~~powershell
Set-Location -LiteralPath 'C:\projects\poputi'
uv python install 3.13
uv sync --locked
~~~

Если `uv` не находится, стандартный установщик обычно размещает его в `$env:USERPROFILE\.local\bin\uv.exe`. Вызовите файл напрямую с оператором `&` или исправьте PATH.

В новой копии, где ещё нет `.env`, создайте его:

~~~powershell
Copy-Item -LiteralPath .env.example -Destination .env
~~~

Оставьте подключение из образца и добавьте в `.env`:

~~~dotenv
POPUTI_RUNTIME_DIR=C:/poputi-data
~~~

Это корень runtime: данные будут в `C:\poputi-data\data`. Нужен доступный для записи путь без кириллицы. Если там уже есть другая база, выберите новый пустой каталог. Существующий `.env`, если он есть, сначала проверьте, а не перезаписывайте.

Загрузите недостающее и запустите:

~~~powershell
.\.venv\Scripts\python.exe -X utf8 scripts\setup_local.py download
.\.venv\Scripts\python.exe -X utf8 scripts\setup_local.py start
.\.venv\Scripts\python.exe -X utf8 manage.py migrate
.\.venv\Scripts\python.exe -X utf8 manage.py seed_demo
.\.venv\Scripts\python.exe -X utf8 manage.py check
.\.venv\Scripts\python.exe -X utf8 manage.py runserver 127.0.0.1:8000
~~~

## 6. Перенос с сохранением пользователей, туров и броней

Используйте дамп PostgreSQL: он переносит структуру, записи, последовательности идентификаторов и историю миграций. Формат `custom` создаётся через `pg_dump -Fc` и восстанавливается через `pg_restore` ([документация PostgreSQL](https://www.postgresql.org/docs/17/app-pgdump.html)).

### На нынешнем ПК

Остановите Django через Ctrl+C, чтобы после копирования не появились новые изменения. PostgreSQL оставьте работающим. Из корня нынешнего проекта:

~~~powershell
New-Item -ItemType Directory -Path .\transfer -Force
$pgBin = 'C:\Users\NotFooound\AppData\Local\Temp\poputi-302c83476c\postgres\pgsql\bin'
& "$pgBin\pg_dump.exe" -h 127.0.0.1 -p 54329 -U poputi -d poputi -W -Fc -f .\transfer\poputi.dump
if ($LASTEXITCODE -ne 0) { throw 'Дамп не создан. Проверьте ошибку PostgreSQL.' }
& "$pgBin\pg_restore.exe" --list .\transfer\poputi.dump
if ($LASTEXITCODE -ne 0) { throw 'Не удалось прочитать оглавление дампа.' }
~~~

Пароль: `poputi_dev`. Путь `$pgBin` соответствует нынешнему runtime; после его переноса укажите новый подкаталог `postgres\pgsql\bin`.

Используется `-f`: бинарный файл записывает PostgreSQL. Не заменяйте его перенаправлением PowerShell `>`.

Скопируйте исходники, `static/` и `transfer/poputi.dump` на новый ПК. Дамп содержит данные пользователей и броней; храните его как копию данных приложения.

### На новом ПК

Подготовьте uv, новое окружение и `.env` по разделу 5, задав новый пустой runtime. Затем выполните **только** загрузку PostgreSQL и создание пустой базы:

~~~powershell
.\.venv\Scripts\python.exe -X utf8 scripts\setup_local.py download
.\.venv\Scripts\python.exe -X utf8 scripts\setup_local.py start
~~~

**До восстановления не запускайте `start.ps1`, `prepare.py`, `migrate` и `seed_demo`: они создают таблицы. Полный дамп нужно восстанавливать в пустую базу.**

~~~powershell
$pgBin = 'C:\poputi-data\postgres\pgsql\bin'
& "$pgBin\pg_restore.exe" -h 127.0.0.1 -p 54329 -U poputi -d poputi -W --no-owner --no-privileges --single-transaction .\transfer\poputi.dump
if ($LASTEXITCODE -ne 0) { throw 'Восстановление не завершено. Исправьте ошибку перед запуском сайта.' }
~~~

Пароль: `poputi_dev`. Параметры `--no-owner` и `--no-privileges` пропускают старых владельцев и права; объекты создаются текущей ролью. `--single-transaction` применяет восстановление целиком либо откатывает при ошибке ([документация pg_restore](https://www.postgresql.org/docs/17/app-pgrestore.html)).

Дамп одной базы не переносит роли PostgreSQL: нужную роль здесь заранее создаёт `setup_local.py start`. Пользователи сайта находятся в `accounts_user` и переносятся вместе с хешами паролей.

После успешного восстановления:

~~~powershell
.\.venv\Scripts\python.exe -X utf8 manage.py migrate
.\.venv\Scripts\python.exe -X utf8 manage.py check
.\.venv\Scripts\python.exe -X utf8 manage.py showmigrations
.\.venv\Scripts\python.exe -X utf8 manage.py shell -c 'from accounts.models import User; from tours.models import Tour, Departure; from bookings.models import Booking; print(User.objects.count(), Tour.objects.count(), Departure.objects.count(), Booking.objects.count())'
.\.venv\Scripts\python.exe -X utf8 manage.py runserver 127.0.0.1:8000
~~~

Сверьте количества записей и проверьте вход прежним аккаунтом, список броней, туры и изображения. При анализе нынешней базы: **2 пользователя, 6 туров, 18 выездов, 1 бронь**. Если данные менялись, сравнивайте с состоянием на момент вашего переноса.

Повторный `seed_demo` после восстановления не требуется. При смене `DJANGO_SECRET_KEY` может понадобиться заново войти на сайт; пароли сохраняются.

Исходную БД и дамп сохраняйте до проверки новой копии. Эти команды не заменяют заполненную целевую базу: при конфликте таблиц используйте новое пустое окружение.

## 7. Перемещение нынешней базы из Temp

Это отдельная операция на том же ПК. Для другого компьютера используйте дамп из раздела 6.

1. Остановите Django.
2. Пока настройки указывают на прежний runtime, остановите БД командой из раздела 4.
3. Убедитесь, что остановка завершилась успешно.
4. Скопируйте **весь** `C:\Users\NotFooound\AppData\Local\Temp\poputi-302c83476c` в новый каталог, например `C:\poputi-data`. Должны появиться `C:\poputi-data\data\PG_VERSION` и `C:\poputi-data\postgres\pgsql\bin\pg_ctl.exe`.
5. Только после копирования добавьте в `.env`: `POPUTI_RUNTIME_DIR=C:/poputi-data`.
6. Запустите БД и сайт, проверьте прежние записи.

Не копируйте работающий каталог `data/` обычным файловым копированием. Не указывайте новый пустой runtime до переноса: скрипт создаст новую БД. Старую копию сохраните до проверки. При смене ОС или основной версии PostgreSQL используйте дамп и восстановление.

## 8. Docker и отдельно установленный PostgreSQL

В Docker данные хранятся в volume `postgres_data`, фактическое имя обычно содержит префикс Compose-проекта. Копирование исходников volume не переносит.

Для Docker остановите переносимый PostgreSQL, запустите Docker Desktop и выполните:

~~~powershell
docker compose up -d db
docker compose ps
.\scripts\start.ps1 -ExternalDatabase
~~~

Дождитесь готовности БД; при необходимости смотрите `docker compose logs db`. Для ручного запуска вместо последней команды выполните `migrate`, при необходимости `seed_demo` и `runserver`, как в разделе 4. Перенос данных в контейнер также требует дампа и восстановления.

Для самостоятельно установленного PostgreSQL заранее создайте роль и базу, задайте подключение в `.env`, например:

~~~dotenv
DATABASE_URL=postgresql://poputi:poputi_dev@127.0.0.1:5432/poputi
~~~

Используйте `-ExternalDatabase` либо запускайте Django вручную без `setup_local.py start`. Локальный скрипт запуска БД использует фиксированные адрес `127.0.0.1:54329`, имя `poputi` и пароль `poputi_dev`: изменение `DATABASE_URL` не меняет параметры этого скрипта.

Переносимая БД и Docker-вариант по умолчанию занимают один порт 54329 и одновременно использовать его не могут.

## 9. Диагностика и проверка

| Проблема | Что проверить |
| --- | --- |
| Python не запускается после переноса | Новое `.venv` через `uv sync --locked`; старое ссылается на путь исходного ПК |
| `uv` не найден | Установка, новый терминал, PATH или прямой вызов `uv.exe` |
| Ошибка подключения | PostgreSQL запущен, `DATABASE_URL` соответствует серверу, порт не занят Docker |
| PostgreSQL не стартует | `postgres.log` в runtime, путь без кириллицы и право записи |
| Отсутствует таблица | Применены ли сохранённые миграции к нужной базе |
| `relation already exists` при восстановлении | Целевая база должна быть пустой: дамп уже включает структуру |
| После перемещения «исчезли» записи | Runtime и `DATABASE_URL`: могла создаться другая база из-за смены пути |
| Нет фотографий | Наличие `static/img/*.jpg`; при необходимости `setup_local.py download` |
| HTTPS-перенаправления при локальном запуске | Для описанного HTTP-запуска нужен `DJANGO_DEBUG=1`; при `0` включаются HTTPS и secure cookies |
| `.env` выглядит верно, но подключение другое | Переменные среды терминала могут переопределять файл |
| Сайт недоступен с другого устройства | Привязка `127.0.0.1` доступна только на том же ПК |

Повторный `start.ps1` не синхронизирует зависимости, если Python виртуального окружения уже существует. После обновления исходников выполните `uv sync --locked` явно.

В `start.ps1` загрузка фотографий вызывается вместе с загрузкой PostgreSQL только при отсутствии его `initdb.exe`. Если перенесли `.tools/postgres/`, но забыли фотографии, выполните `setup_local.py download` явно.
