# Предлагаемый стек и организация BDD

Статус: стек выбран. Создано приложение на Python 3.13, Django 5.2 и PostgreSQL; точные версии зависимостей закреплены в `uv.lock`. Инструкция запуска находится в `README.md` в корне проекта.

## Стек

| Часть | Рекомендация | Причина |
| --- | --- | --- |
| Язык сервера | Python 3.13 | Совместим с выбранной веткой Django и инструментами тестирования |
| Сервер | Django 5.2 LTS с актуальным исправлением | Авторизация, формы, ORM, миграции, шаблоны и административный интерфейс в одном фреймворке |
| Страницы | Шаблоны Django, HTML, CSS и обычный JavaScript | Сервер формирует страницы, JavaScript добавляет интерактивность |
| База данных | PostgreSQL | Подходит для коротких транзакций с блокировкой выезда на время проверки и резервирования мест |
| Автоматизация BDD | pytest и pytest-bdd | Связывают Gherkin-сценарии с Python-функциями и запускают их как тесты |
| Интеграция тестов с Django | pytest-django | Предоставляет тестовую базу, HTTP-клиент и средства тестирования транзакций |
| Проверка браузерных путей | Playwright с pytest-playwright | Проверяет реальное взаимодействие через страницы, формы и JavaScript |

Ветка Django 5.2 LTS получает расширенную поддержку до апреля 2028 года. Точные версии зависимостей нужно закрепить при создании окружения.

## Выбор базы данных

SQLite подходит для небольшого локального проекта при корректной организации операций записи. Бронирование не требует PostgreSQL само по себе.

Для этого проекта предлагается PostgreSQL: учёт мест при одновременных запросах является центральным поведением, а Django поддерживает для PostgreSQL блокировку строк через `select_for_update()` внутри транзакции. SQLite не поддерживает эту операцию блокировки строк.

Ни одна база сама по себе не предотвращает переполнение выезда. Проверка мест, создание брони и операции отмены должны использовать согласованные транзакции. Проверки конкурентного бронирования нужно выполнять на той же СУБД, для которой написан этот механизм.

## Где писать сценарии

Сценарии хранятся в проекте как обычные UTF-8 файлы с расширением `.feature`. Их можно редактировать в VS Code, PyCharm или другом редакторе. Цели и словарь хранятся в `docs/`, а исполняемые шаги — в Python-модулях тестов.

Предлагаемая структура после создания приложения:

```text
BDD/
  docs/
    product.md
    stack.md
  features/
    catalog/
      browse_tours.feature
      find_departures.feature
    accounts/
      registration.feature
      authentication.feature
    tours/
      manage_tours.feature
      manage_departures.feature
      view_departure_bookings.feature
    bookings/
      create_booking.feature
      cancel_booking.feature
      view_bookings.feature
  tests/
    bdd/
      conftest.py
      test_booking.py
    e2e/
      test_booking_journey.py
  config/
  accounts/
  tours/
  bookings/
  templates/
  static/
  manage.py
  pyproject.toml
```

Созданы приложения `accounts`, `tours`, `bookings`, шаблоны и статические файлы, миграции и тесты. Все семь возможностей описаны десятью `.feature` файлами. Четыре файла уже связаны с Python-шагами в `tests/bdd/test_core.py`: регистрация, вход/выход, бронирование и отмена. Остальные спецификации и браузерные тесты Playwright — следующие этапы; текущий интерфейс проверен через браузер вручную.

## Как выглядит фича

- В одном `.feature` файле описывается одна возможность и связанные с ней сценарии.
- Начало `# language: ru` позволяет использовать русские ключевые слова Gherkin.
- `Функциональность` называет возможность, свободный текст ниже объясняет пользу.
- `Сценарий` описывает один конкретный пример.
- `Дано` задаёт исходное состояние, `Когда` — действие, `Тогда` — наблюдаемый результат. `И` продолжает предыдущую группу шагов.
- Успешный результат, отказ, границы количества мест и конкуренция запросов описываются отдельными сценариями.
- SQL, названия HTML-элементов и детали работы ORM находятся в реализации шагов, когда они нужны для проверки.

## Как сценарий становится тестом

Python-модуль в `tests/bdd/` связывает сценарии с pytest-bdd через `scenario` или `scenarios`. Функции с декораторами `given`, `when`, `then` реализуют текст шагов. Названия декораторов остаются английскими даже при русском тексте сценария.

Основные правила проверяются через код приложения и HTTP-клиент Django. Ключевые пользовательские пути дополнительно проверяются в браузере. Тест одновременных запросов должен действительно использовать отдельные соединения и пересекающиеся операции; последовательная отправка двух запросов этого случая не проверяет.

После подключения шагов и настройки тестового окружения запуск выполняется командой `python -m pytest`. Один `.feature` файл без Python-шагов и привязки сценариев ещё не является автоматическим тестом.

Для каждой небольшой возможности рабочий цикл такой: обсудить примеры, записать сценарий, связать его с проверкой, получить ожидаемое падение, реализовать поведение и добиться прохождения проверки.
