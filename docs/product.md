# Цели и основные возможности сайта авторских туров

Документ фиксирует принятые решения и предлагает состав первой версии. Исходный файл «Фичи.docx» используется как набор заметок. Стек описан отдельно в `docs/stack.md`.

## Принятые решения

- Основной результат работы сайта — бронирование мест с учётом доступности.
- Если мест достаточно, бронь подтверждается сразу.
- В первой версии нет онлайн-оплаты.
- Роль «Студия» не нужна.

## Цели

1. Путешественник может найти тур, выбрать выезд и забронировать нужное количество мест.
2. Организатор может публиковать свои туры, задавать выезды и видеть бронирования.
3. Система сохраняет корректное число свободных мест при бронировании, отмене и одновременных запросах.
4. Правила поведения описаны конкретными BDD-сценариями и при реализации проверяются автоматически.

## Словарь предметной области

| Понятие | Значение |
| --- | --- |
| Тур | Описание предложения: название, направление, категория, программа и организатор |
| Выезд | Проведение тура в конкретные даты, с определённой вместимостью и ценой за место |
| Бронь | Подтверждённое резервирование заданного количества мест на одном выезде для пользователя |
| Свободные места | Вместимость выезда за вычетом мест в действующих подтверждённых бронях |
| Организатор | Пользователь, которому принадлежит тур; в предлагаемой модели это отношение к туру, а не отдельная обязательная роль аккаунта |

У одного тура может быть несколько выездов. Места бронируются на выбранный выезд. Например, у тура «Алтай» выезд в июне и выезд в июле имеют отдельную доступность.

## Предлагаемый состав первой версии

| Код | Возможность | Результат для пользователя |
| --- | --- | --- |
| F01 | Просмотр каталога и карточки тура | Посетитель знакомится с программой, организатором и предстоящими выездами |
| F02 | Подбор подходящего выезда | Посетитель ищет по названию и направлению, фильтрует по категории, датам и цене; при необходимости сортирует результаты |
| F03 | Регистрация и вход | Пользователь получает аккаунт для своих броней и публикаций; может завершить сеанс |
| F04 | Публикация и управление своими турами и выездами | Организатор меняет описание, даты, цену и вместимость принадлежащих ему предложений |
| F05 | Бронирование мест | Пользователь выбирает выезд и количество мест, получает подтверждение при достаточной доступности |
| F06 | Просмотр и отмена своих броней | Пользователь видит свои брони, отменяет разрешённые к отмене; освобождённые места возвращаются в доступность |
| F07 | Просмотр бронирований своих выездов | Организатор видит список броней и число занятых и свободных мест |

Это список возможностей продукта. При детализации крупная возможность может быть разбита на несколько `.feature` файлов. Например, создание брони и её отмена имеют разные сценарии.

## Предлагаемые правила первой версии

Следующие правила — рабочее предложение для детализации, а не требования из исходных заметок:

- Просмотр и подбор доступны гостю. Для бронирования и публикации нужен вход в аккаунт.
- Любой зарегистрированный пользователь может публиковать туры и бронировать выезды. Отдельный тип аккаунта организатора не требуется.
- Бронируется целое положительное количество мест. Частичное подтверждение запроса не применяется.
- Подтверждённая бронь сразу занимает места; сама по времени не истекает.
- Бронирование разрешено для будущего открытого выезда.
- Пользователь видит и отменяет только свои брони. Предлагаемый срок отмены — до начала выезда.
- Отмена возвращает места ровно один раз. Повторная отмена не увеличивает доступность.
- Организатор меняет только свои туры и выезды и видит брони только своих выездов.
- Вместимость нельзя уменьшить ниже числа уже забронированных мест.
- Тур или выезд с историей бронирований сохраняется в архиве. Прекращение будущих продаж не отменяет существующие брони.

### Детали, выбранные для первого набора сценариев

Это рабочие продуктовые решения, добавленные при детализации фич. Их можно пересмотреть до реализации соответствующего поведения.

- Для регистрации используются логин, пароль и подтверждение пароля. Логин уникален, пароль содержит не менее 8 символов. После успешной регистрации пользователь сразу входит в аккаунт. При ошибке входа показывается единое сообщение «Неверный логин или пароль».
- Название, направление, категория и программа тура обязательны. Тур публикуется сразу после корректного создания. Изображение пока не является обязательным полем.
- Каталог показывает опубликованные туры, в том числе туры без доступных выездов. Карточка и подбор показывают будущие открытые выезды опубликованных туров. Выезд с нулём мест виден, но новую бронь получить нельзя. Прошедшие, закрытые и архивные выезды не показываются в публичной подборке.
- Поиск проверяет вхождение текста в название тура или направление без учёта регистра; пробелы по краям запроса игнорируются. Пустой запрос не ограничивает результат.
- Фильтры категории, даты начала выезда и цены за место применяются совместно с поиском. Обе границы диапазонов включаются. При неправильном диапазоне показана ошибка, список подборки не выводится.
- Основной порядок выездов — по возрастанию даты начала. Дополнительная сортировка — по цене за место по возрастанию или убыванию. При равной цене сначала идёт более ранний выезд; при равной дате — по названию тура. Сортировка сохраняет текущие фильтры.
- Цена за место указывается в рублях и должна быть положительной. Вместимость — целое положительное число. Начало нового выезда должно быть в будущем, окончание — строго после начала. Время сравнивается с учётом часового пояса; в примерах используется Europe/Moscow.
- Даты и цену выезда можно менять только до появления истории бронирований. После первого бронирования, даже отменённого впоследствии, эти условия фиксируются. Вместимость разрешено менять, сохраняя ограничение по занятым местам.
- Пользователь может создать несколько отдельных броней на один выезд. Повторная отправка того же запроса возвращает сведения об исходной брони и не списывает места повторно. Для новой брони требуется отдельное намеренное действие пользователя.
- Новая бронь и отмена существующей брони разрешены строго до момента начала выезда. В сам момент начала обе операции уже запрещены.
- Закрытие или архивирование не отменяет существующие брони и не скрывает их от владельца и организатора. Владелец может отменить такую бронь до начала выезда; освободившиеся места не открывают закрытые продажи автоматически.
- Личный список показывает как подтверждённые, так и отменённые брони. Организатор также видит оба состояния своих выездов, но в число занятых входят только места подтверждённых броней.

## Обязательные свойства учёта мест

- Число занятых мест не превышает вместимость выезда.
- Число свободных мест не бывает отрицательным.
- При отказе в бронировании места не списываются и подтверждённая бронь не появляется.
- Проверка доступности и подтверждение брони выполняются как одна согласованная операция.
- Если на последнее место одновременно претендуют два пользователя, подтверждение получает только один.

## Спецификации поведения

Все семь возможностей покрыты файлами в `features/`. Регистрация и вход, управление турами и выездами, просмотр и отмена броней разделены на самостоятельные функциональности. Карта файлов и правила чтения находятся в [оглавлении сценариев](../features/README.md).

В сценариях есть успешные действия, ошибки данных, запреты доступа, границы доступности и одновременные запросы. Временные условия задаются явно, поэтому примеры не зависят от текущей календарной даты и часового пояса компьютера.

Регистрация, вход/выход, создание и отмена брони уже реализованы и связаны с Python-шагами. Выполняются 39 BDD-примеров из четырёх файлов и 17 дополнительных HTTP/интеграционных проверок. Каталог, карточка тура, поиск и фильтрация также реализованы. Пользовательский кабинет организатора и автоматизация остальных спецификаций относятся к следующим этапам.

## Что уточнить перед реализацией соответствующих фич

- Действия при отмене выезда организатором и способ уведомить участников.
- Дополнительные сведения об участниках и контактные данные, если они понадобятся организатору.
- Нужны ли дополнительные способы сортировки, изображения и восстановление архивных предложений.

Отзывы, избранное, переписка, лист ожидания, промокоды и онлайн-оплата могут быть добавлены после основного цикла бронирования.

## Порядок разработки

1. Описать и реализовать бронирование при достаточном количестве мест и отказ при их нехватке.
2. Проверить одновременное бронирование последних мест на выбранной базе данных.
3. Реализовать просмотр и отмену своих броней с возвратом мест.
4. Добавить управление турами и выездами, каталог и подбор.
5. Собрать браузерный путь от входа в аккаунт до подтверждения и отмены брони.

Для первых шагов данные можно готовить тестовыми фикстурами. Это позволяет сначала проверить главное правило продукта, затем подключить пользовательские страницы.
